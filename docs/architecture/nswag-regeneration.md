# NSwag Client Regeneration

## What it is

`ClientApp/src/api/web-api-client.ts` is **auto-generated** by NSwag v14.5.0.0
(NJsonSchema v11.4.0.0, Newtonsoft.Json v13.0.0.0) from the backend OpenAPI
specification. It must **never be edited manually** — all changes will be
overwritten on the next regeneration.

The hand-authored `AuthorizedApiBase` class (lines 10–35) is placed **above**
the auto-generated block. Verify after every regeneration that it is still present
and unmodified.

## When to regenerate

Regenerate when:
- A backend API endpoint is added, removed, or its signature changes
- A new DTO (data transfer object) is added or modified in the backend schema
- The OpenAPI spec version is bumped

Do **not** regenerate solely for frontend refactoring — the generated client is
stable until the backend contract changes.

## Regeneration procedure

### Prerequisites

```bash
npm install -g nswag   # version 14.x to match current file header
node --version         # must be >= 18
```

### Steps

1. **Obtain the OpenAPI spec** from the running backend or published URL:

   ```bash
   curl http://localhost:5000/swagger/v1/swagger.json -o api-spec.json
   ```

2. **Check for an existing NSwag config file** at the project root:

   ```bash
   ls *.nswag nswag.json 2>/dev/null
   ```

   If a config file exists, run:
   ```bash
   nswag run nswag.json
   ```

   Otherwise regenerate manually:
   ```bash
   nswag openapi2tsclient \
     /input:api-spec.json \
     /output:ClientApp/src/api/web-api-client.ts \
     /template:Fetch \
     /typeStyle:Class \
     /generateConstructorInterface:false \
     /generateOptionalParameters:true \
     /nullValue:Undefined \
     /generateClientInterfaces:false
   ```
   Adjust flags to match the existing generated file's style (inspect the
   `<auto-generated>` comment block for the original generation command).

3. **Verify `AuthorizedApiBase` is preserved** — the file must still contain:

   ```ts
   export class AuthorizedApiBase {
       authToken = '';
       targetOrganisation = sessionStorage.getItem('targetOrganisation');
       setAuthToken(token: string) { ... }
       protected transformOptions(options: any): Promise<any> { ... }
   }
   ```

   If NSwag overwrites this class, restore it from source control and insert it
   immediately before the first generated `export class` statement.

4. **Run the unit test suite:**

   ```bash
   npx vitest run tests/unit/
   ```

   All tests must pass. Any failures indicate the API contract changed in a way
   that breaks existing component behaviour — investigate before merging.

5. **Update Storybook MSW handlers** (`.storybook/msw-handlers.ts`) if new API
   endpoints were added that require mock responses for stories.

6. **Search for usages of removed/renamed methods:**

   ```bash
   grep -rn "client\." ClientApp/src --include="*.ts" --include="*.tsx" | grep -v "node_modules"
   ```

   Ensure no component still calls a method that was removed in the new schema.

## Rebuild note

In the rebuilt portal, consider generating the NSwag client into a dedicated
`packages/api-client/` workspace. This isolates regeneration from the main
application code and avoids the `AuthorizedApiBase` preservation concern — the
hand-authored class can live in the application layer and compose with the
generated client via dependency injection.
