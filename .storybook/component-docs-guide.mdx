# Writing component documentation

Storybook documentation combines inferred component metadata with executable
stories. Keep each kind of information in its natural source so the docs stay
accurate as the implementation changes.

## Autodocs policy

Autodocs is enabled globally by `.storybook/preview.ts`:

```ts
tags: ['autodocs'];
```

Normal component story files do not repeat this tag. A typical story module is:

```tsx
import type { Meta, StoryObj } from '@storybook/react-vite';
import MyComponent from './MyComponent';

const meta = {
  component: MyComponent,
} satisfies Meta<typeof MyComponent>;

export default meta;
type Story = StoryObj<typeof meta>;

export const Default: Story = {
  args: {
    children: 'Example',
  },
};
```

### Opting out

Use Storybook's negative tag syntax when a component or story should not
participate in Autodocs:

```ts
const meta = {
  component: InternalComponent,
  tags: ['!autodocs'],
} satisfies Meta<typeof InternalComponent>;
```

A single story can also remove the inherited tag:

```ts
export const InternalState: Story = {
  tags: ['!autodocs'],
};
```

Do not use `'docs'` as an Autodocs activation tag.

## Configuration ownership

Keep Storybook behaviour in one predictable layer:

- `.storybook/main.ts` owns the React/Vite framework, story globs, addons,
  documentation naming, MDX compilation, docgen, static assets, and the minimum
  Vite compatibility configuration.
- `.storybook/preview.ts` uses `definePreview` and owns project annotations:
  global Autodocs activation, decorators, lifecycle hooks, accessibility,
  Controls, Code Panel, Source behaviour, styles, and preview addons. Compose
  `addonDocs()` here so Docs supplies its renderer annotations to
  `definePreview` while `main.ts` retains preset and MDX build ownership.
- CSF metadata owns component and story exceptions.
- MDX owns narrative documentation and deliberate Doc Block composition.

There is no `.storybook/preview-docs.ts` or cloned Autodocs page. Standard
Autodocs remains the baseline so Storybook upgrades improve documentation
without requiring a parallel project template.

## Metadata responsibilities

- TypeScript owns public prop types and required or optional state.
- JSDoc owns semantic component and prop descriptions, constraints, usage
  intent, and deprecation information.
- CSF stories own executable examples and interactive states.
- Args represent runtime story state.
- ArgTypes augment inferred metadata when Storybook needs extra presentation or
  control information.
- Parameters configure Storybook at project, component, or story scope.
- MDX owns narrative or exceptional documentation.
- Doc Blocks compose MDX and custom documentation pages.

### TypeScript and JSDoc

Write meaningful descriptions for public props:

```ts
interface ButtonProps {
  /** Visible label or content rendered by the button. */
  children: React.ReactNode;

  /** Visual treatment used to express the action's semantic importance. */
  variant?: 'primary' | 'secondary';

  /** Prevents pointer and keyboard activation when true. */
  disabled?: boolean;
}
```

Do not restate the type without adding meaning. For example, `/** Disabled. */`
does not improve a `disabled?: boolean` declaration.

## Args and ArgTypes

### Args

`args` are runtime values passed to a story:

```ts
export const Primary: Story = {
  args: {
    variant: 'primary',
    disabled: false,
  },
};
```

Prefer args over custom render functions when args can express the state.

### ArgTypes

`argTypes` describe how Storybook documents or controls values:

```ts
const meta = {
  component: PrimaryButton,
  argTypes: {
    variant: {
      options: ['primary', 'secondary'],
      control: 'inline-radio',
      table: {
        category: 'Appearance',
      },
    },
  },
} satisfies Meta<typeof PrimaryButton>;
```

Prefer inferred ArgTypes. Add manual ArgTypes only for semantics TypeScript and
JSDoc cannot express clearly, such as control behaviour, options, mappings,
conditional display, categories, or intentional hiding.

## Parameters and configuration scope

Storybook parameters are static metadata used by stories and addons.
Configuration is inherited from least specific to most specific:

```text
project (preview.ts)
        ↓
component (meta)
        ↓
story
```

More specific configuration overrides inherited configuration. Put
project-wide policy in `preview.ts`; use component or story Parameters only for
deliberate exceptions.

```ts
export const ComplexExample: Story = {
  parameters: {
    docs: {
      source: {
        type: 'code',
      },
    },
  },
};
```

## Network mocking

Docs and the MSW v3 preview addon are registered through `definePreview`:

```ts
import addonDocs from '@storybook/addon-docs';
import addonMsw from 'msw-storybook-addon';

const preview = definePreview({
  addons: [addonDocs(), addonMsw()],
});
```

The project supplies a custom worker setup in `preview.ts` so shared handlers
and the same-origin request policy have one owner. Story-specific handlers use
the story lifecycle instead of deprecated `parameters.msw`:

```ts
export const EmptyState: Story = {
  beforeEach({ msw }) {
    msw.use(emptyResponseHandler);
  },
};
```

Handlers added with `msw.use` are reset between stories by the addon.

## JSDoc and executable examples

Use JSDoc for semantic documentation:

- component purpose;
- prop meaning;
- constraints;
- usage intent;
- deprecation information.

Use CSF stories for executable examples, interactive states, source snippets,
Controls, Code Panel output, and regression coverage. A JSDoc `@example` may
still help IDE consumers, but it is not the project's canonical Storybook
example mechanism.

## Internal APIs

`@internal` is a source-code documentation convention. Do not rely on it as a
Storybook visibility control unless repository tooling explicitly implements
that behaviour. Use `!autodocs` for Storybook documentation visibility.

To keep a prop available while omitting it from the API table:

```ts
argTypes: {
  internalProp: {
    table: {
      disable: true,
    },
  },
},
```

## Source and Code Panel

The project enables the Code Panel globally:

```ts
parameters: {
  docs: {
    codePanel: true,
  },
},
```

The Code Panel and Source Doc Block share `parameters.docs.source`:

```ts
parameters: {
  docs: {
    source: {
      type: 'auto',
      excludeDecorators: true,
    },
  },
},
```

Override this only when a specific story needs different source behaviour.

## When to use Autodocs and when to use MDX

Use Autodocs for the normal component baseline: description, API metadata,
Controls, stories, and source examples.

Use MDX for narrative material that cannot be derived cleanly from component
metadata, including design and accessibility guidance, cross-component
workflows, comparisons, architecture, and migrations.

For a component-specific custom page, attach MDX to the story-module exports:

```mdx
import { Canvas, Controls, Meta } from '@storybook/addon-docs/blocks';
import * as ButtonStories from './Button.stories';

<Meta of={ButtonStories} />

# Button

Use buttons to trigger actions.

<Canvas of={ButtonStories.Primary} />

## API

<Controls />
```

Always pass the full story-module exports to `<Meta of={...} />`, not the
component itself.

## Doc Blocks

### Core component documentation

`Meta`, `Description`, `Primary`, `Story`, `Stories`, `Canvas`, `Source`,
`Controls`, and `ArgTypes`.

### Design-system documentation

`ColorPalette`, `Typeset`, and `IconGallery`.

### Structural and utility documentation

`Title`, `Subtitle`, `TableOfContents`, `Markdown`, and `Unstyled`.

Do not use every block merely because it exists. Choose the block that solves
the documentation problem.

## Tables in MDX

Use standard Markdown tables for simple static documentation. `remark-gfm` is
enabled by the Storybook Docs configuration to support GFM table syntax.

Use the shared `DocsTable` component only when a table requires custom
behaviour, semantics, or presentation beyond Markdown. The Storybook-specific
table stylesheet remains necessary because Bootstrap Reboot affects plain
Markdown table presentation.

## Verification

Documentation must build successfully in CI. Run these gates from the repository
root:

```bash
npm run type-check
npm run lint
npm run lint:mdx
npm run test:unit
npm run test:storybook
npm run storybook:verify:docs
npm run test:e2e:storybook
```

Use the Storybook MCP `run-story-tests` tool for focused feedback while editing
stories and for the final broad Storybook pass. Keep stable story IDs where
possible so executable coverage does not drift.

The static documentation verifier applies strict generated-prop-metadata checks
to Reusable components with public props. Prop-less shells and composite gallery
stories require a named, reasoned exception; the verifier fails when an exception
becomes stale so it can be removed. Route and page stories are validated as
executable examples by the Storybook build, interaction tests, and Storybook BDD
suite rather than being forced to expose a reusable component API.
