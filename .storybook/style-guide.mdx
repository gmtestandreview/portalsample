# Style Guide

**NMI Portal visual language, content style, and UI usage patterns**

This style guide defines the baseline visual and content standards for the NMI customer portal. It is intended to keep components consistent, accessible, and predictable across all user flows.

## Design Principles

- **Clarity first**: users should understand what to do in under 5 seconds.
- **Consistency over novelty**: reuse established patterns before inventing new ones.
- **Accessibility by default**: every UI decision must support keyboard and assistive technology use.
- **Government-grade trust**: plain language, transparent feedback, and stable interactions.

### Type Rules

- Use sentence case for headings and labels.
- Keep body copy concise and action-oriented.
- Prefer explicit verbs in buttons and links (for example: "Save changes", "Continue", "Download certificate").
- Avoid ambiguous microcopy such as "Submit" when a specific action is known.

### Color Usage Rules

- Never use color as the only means of conveying meaning.
- Ensure contrast meets WCAG 2.1 AA for text and controls.
- Reserve semantic colors for status messaging, not decorative emphasis.
- Keep backgrounds subtle so form content remains dominant.

## Component Writing Style

### Buttons

- Primary button: one dominant action per section.
- Secondary button: alternatives such as cancel/back.
- Labels should communicate outcomes, not generic actions.

### Alerts

- Success/Info/Warning should be polite; Error should be assertive.
- Keep messages specific and include recovery guidance where possible.
- Prefer one alert per section unless severity differs clearly.

### Forms

- Place labels above fields.
- Show validation near the field and in summary for long forms.
- Preserve user input after validation errors whenever possible.

## Interaction Standards

- Keyboard focus must always be visible.
- Disabled controls should include clear rationale in nearby copy when relevant.
- Loading states should preserve layout and indicate progress.
- Avoid blocking overlays unless there is no safe non-blocking alternative.

## Content Standards

- Use plain English and avoid internal acronyms where possible.
- Prefer active voice.
- Keep helper text under 140 characters when feasible.
- Error text should explain what happened and what to do next.

## QA Checklist

Before shipping any new UI:

1. Check contrast and focus states.
2. Navigate flow with keyboard only.
3. Validate screen reader announcements for alerts and errors.
4. Confirm story variants exist for default, edge, and error states.
5. Ensure copy tone matches the rest of the portal.
6. If Storybook BDD coverage exists for changed stories, run `npx bddgen` then `npx playwright test --grep "@storybook" --reporter=list`.
