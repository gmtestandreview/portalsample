Architect observations

  • Bootstrap is a fan-out hub. App.tsx and index.tsx import every route module directly. There is no lazy-loading or code-splitting at the route level, meaning the initial bundle includes all wizard route code even for unauthenticated users.
  • WizardRoutedStep is a chokepoint. Every multi-step form (Account, Contact, RFQ, Accept Quote) flows through WizardRoutedStep. Its current [key: string]: any prop interface means a bug there affects all four workflows simultaneously with no compile-time warning.
  • API Client is a hidden dependency of Storage. web-api-client.ts reads sessionStorage directly (dotted edge) rather than via the typed storage/* layer, creating a bypass of the application's abstraction boundary.
  • PreConditions wraps all auth-gated routes but is also coupled to ModalContext. Extracting modals into a sibling context rather than a child of PreConditions would reduce the coupling between navigation guards and modal state.
  • Validation is a clean leaf node — no inbound dependencies from UI or API layers. This is the correct shape and makes schema migration safe.

Architect observations

  • Accept Quote touches 5 API clients — the widest API footprint of any domain. It reads quote details (QuoteClient), loads org data for the report recipient step (AccountsClient), fetches delivery options (ApplicationClient), polls instrument status (DashboardClient), and submits acceptance (AcceptQuoteClient). A failure in any one of those five during the wizard flow has no offline/partial-save fallback.
  • targetOrganisation in sessionStorage is a shared-write, multi-read pattern. Only AccountProvider writes it, but 4 API client classes read it directly at instantiation time (dotted edges). This creates a hidden time-of-check/time-of-use window: a branch switch between wizard steps would leave in-flight API calls using the old ABN.
  • DashboardClient is the most heavily shared API client — consumed by Dashboard, Accept Quote, Measurement Reports, and Shared Route Helpers. Its contract stability is a migration dependency for three separate domains.
  • No domain writes to QuoteClient — it is read-only from the portal's perspective. Quote creation is a server-side process; the portal only reads the result. This means QuoteClient could be extracted to a lightweight read-only SDK without breaking any write flows.
  • sessionStorageCache is only used by Account Management — specifically for caching ABN lookup results. This is an under-leveraged mechanism; other lookup-heavy steps (RFQ instrument type dropdowns) repeat API calls on every re-render rather than using the cache.

Architect observations

  • The happy path passes through 7 sequential network calls before the user can start entering RFQ data (signIn → getDashboard ×3 → getAccountDetails → getApplicationOptions → then step 2 adds more). None of these calls are parallelised within the wizard steps — each loadStep closure fires sequentially. This is the most likely source of perceived slowness on first use.
  • PreConditions is a synchronous redirect gate with no loading state. If AccountLoginClient.signIn is slow, the gate check runs before account data is fully loaded, potentially redirecting a legitimate user to /create-account on a slow connection. There is no pending/loading guard between the signIn response and the PreConditions check.
  • Draft save happens only on step-exit (Save & Exit), not on navigation between steps. A browser crash between Step 2 and Step 3 loses all unsaved progress. The UnsavedFormPrompt blocks React Router navigation but cannot block browser close or refresh.
  • The token acquisition pattern repeats at every step transition. acquireTokenSilent is called in both loadStep and saveStep of each *Props.ts file. If the MSAL cache is warm, this is fast; if it requires an iframe round-trip, it adds latency to every step. A single token interceptor would eliminate this repeated cost.
  • No production telemetry is available to ground-truth these observations. The Azure Application Insights workspace for this environment should be queried for customEvents and requests telemetry to validate which steps have the highest p99 variance before prioritising performance work.
