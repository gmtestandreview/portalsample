# Project Management Document Review Checklist

**Audience:** Senior Executives and Project Stakeholders **Purpose:** To ensure
that project artefacts (e.g., reports, change requests, plans, logs) meet
high-quality standards, support decision-making, and comply with organisational
governance.

---

## Section I – General Quality Criteria (Applicable to All Project Artefacts)

| **Criterion**                       | **Description**                                                                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Clarity**                         | Document is written in plain, executive-friendly language that avoids technical jargon unless necessary.                              |
| **Humanised Language**              | Uses a natural, conversational tone appropriate for humans—not overly formal, robotic, or AI-generated.                               |
| **Syntactic Quality**               | Sentences are grammatically correct, well-punctuated, and follow standard structural conventions.                                     |
| **Semantic Quality**                | Content conveys unambiguous meaning, logically consistent, and free from misinterpretation.                                           |
| **Pragmatic Quality**               | Information is relevant, purposeful, and supports action or decision-making.                                                          |
| **Localization & Style Compliance** | Conforms to **Australian grammar** and the **Australian Government Style Manual** for clarity, spelling, punctuation, and formatting. |
| **Correctness**                     | Content is factually accurate, free from errors, and validated against approved data sources.                                         |
| **Completeness**                    | No essential content is omitted; document includes all required elements for its type.                                                |
| **Consistency**                     | Terminology, layout, and structure are consistent across the document and with related artefacts.                                     |
| **Traceability**                    | References to business cases, baselines, decisions, or approvals are clear and accessible.                                            |
| **Modifiability**                   | Document can be efficiently updated, is well-organised, and version-controlled if required.                                           |
| **Governance Alignment**            | Complies with the applicable project governance framework (e.g., PRINCE2, PMBOK, agency-specific processes).                          |

---

## Section II – Project Status Reports

| **Criterion**                  | **Description**                                                                                |
| ------------------------------ | ---------------------------------------------------------------------------------------------- |
| **Timeliness**                 | Reflects current status and adheres to reporting cycle.                                        |
| **Performance Indicators**     | Reports on scope, time, cost, and quality baselines with variance commentary.                  |
| **Milestone Tracking**         | Clearly identifies milestone status with reasons for delay or changes.                         |
| **Risk & Issue Summary**       | Highlights key risks/issues with owners, impacts, and treatment progress.                      |
| **Benefit Realisation Update** | Indicates progress towards anticipated benefits; highlights deviations.                        |
| **Stakeholder Relevance**      | Tailored to the needs of executive readers; includes summaries or dashboards where applicable. |

---

## Section III – Change Requests

| **Criterion**                 | **Description**                                                                   |
| ----------------------------- | --------------------------------------------------------------------------------- |
| **Business Rationale**        | Clearly articulates the reason for the change and its business value.             |
| **Impact Assessment**         | Identifies implications for scope, schedule, cost, quality, resources, and risks. |
| **Alternatives Considered**   | Notes options evaluated and reasons for chosen course.                            |
| **Approvals and Authority**   | Demonstrates decision history with sign-offs (aligned to RACI).                   |
| **Traceability to Baselines** | Identifies affected requirements, plans, or deliverables.                         |
| **Feasibility and Risk**      | Describes implementation feasibility and any new risks introduced.                |

---

## Section IV – Risk and Issue Logs

| **Criterion**                      | **Description**                                                 |
| ---------------------------------- | --------------------------------------------------------------- |
| **Defined Using Standard Format**  | Risk = Cause → Event → Effect; Issues are problem-focused.      |
| **Current Status and Assignment**  | Updated with realistic ratings, due dates, and assigned owners. |
| **Clear Response Strategies**      | Actions are categorised and specific (e.g., mitigate, avoid).   |
| **Residual Risk Analysis**         | Includes after-action risk ratings and rationales.              |
| **Timing/Proximity Consideration** | Identifies expected timeframes for risk occurrence.             |
| **Escalation and Status Tracking** | Shows history of escalations and decisions.                     |

---

## Section V – Benefits Realisation Plans

| **Criterion**                    | **Description**                                                             |
| -------------------------------- | --------------------------------------------------------------------------- |
| **Defined Benefit Statements**   | Benefits clearly described as financial/non-financial, tangible/intangible. |
| **SMART KPIs**                   | Includes measurable indicators with baseline and targets.                   |
| **Ownership and Timeline**       | Assigned benefit owners with defined realisation schedules.                 |
| **Dependencies Identified**      | Links to enabling initiatives or outputs are articulated.                   |
| **Realisation Risk Identified**  | Highlights risks to achieving the benefit.                                  |
| **Ongoing Measurement Approach** | Describes how benefits will be tracked post-implementation.                 |

---

## Section VI – Planning Documents (PMPs, Schedules, WBS)

| **Criterion**            | **Description**                                                                  |
| ------------------------ | -------------------------------------------------------------------------------- |
| **Charter Alignment**    | Objectives, scope, and assumptions consistent with the approved Project Charter. |
| **WBS Completeness**     | Work Breakdown Structure decomposes all deliverables to a sufficient level.      |
| **Schedule Feasibility** | Activities logically sequenced, dependencies noted, and critical path visible.   |
| **Resource Planning**    | Clearly specifies required skills, availability, and assigned roles.             |
| **Quality Planning**     | Defines quality control and assurance processes.                                 |
| **Baseline Definition**  | Scope, cost, and time baselines are defined and linked to change control.        |

---

## Section VII – Agile Artefacts (Backlogs, Features, PI Objectives)

| **Criterion**                          | **Description**                                                            |
| -------------------------------------- | -------------------------------------------------------------------------- |
| **INVEST-Style Stories**               | Stories are Independent, Negotiable, Valuable, Estimable, Small, Testable. |
| **Acceptance Criteria Included**       | Every story or feature has verifiable acceptance criteria or examples.     |
| **Prioritisation Justified**           | Items prioritised using value-driven methods (e.g., MoSCoW, WSJF).         |
| **Definition of Done (DoD)**           | Shared understanding of completion across stories and teams.               |
| **Iteration & PI Objectives Captured** | Objectives are measurable and timeboxed.                                   |
| **Traceable to Strategic Outcomes**    | Stories and features mapped to business goals or benefits.                 |
